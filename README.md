# LoRaPedia

**An offline Wikipedia you can text over a Meshtastic mesh.**

Someone on your LoRa mesh sends a question as a normal text message. LoRaPedia searches a local copy of
Wikipedia, has a small local language model write a short answer from what it found, and replies over the
mesh, trimmed to fit Meshtastic's tiny message size. No internet, no cloud, no telemetry while it runs.

It is inspired by Project NOMAD, but focused on one job: answers delivered over the mesh.

> **How this was made:** this entire project, code, tests, documentation and release pipeline, was generated by AI
> ([Claude](https://claude.com/claude-code), through Claude Code) under the direction of a human, who decided what to build,
> steered the design and tested it on real hardware. Read it, and the AI's answers it relays, with that in mind.

```
  Person on the mesh:   what is a quasar?
  LoRaPedia:            A quasar is an extremely luminous active galactic nucleus powered by a
                        supermassive black hole that is accreting matter.                  118/200 B
```

A web interface runs the whole thing: a setup wizard, a live feed of every question and answer, and pages for
the Wikipedia library, the model, and the radio. A non-technical person can set it up in about ten minutes.

## What you need

| | Minimum | Comfortable |
|---|---|---|
| **Computer** | Any 64-bit x86 or ARM64 machine: mini PC, laptop, Raspberry Pi 5, Jetson | Same, with more memory |
| **Memory** | 4 GB (1B model, small Wikipedia file) | 8 to 16 GB (3B model) |
| **Disk** | 3 GB free (Quick Reference plus a model) | 50 GB+ for Complete (Compact); see the package table |
| **GPU** | Not needed | Makes answers faster; an NVIDIA card with 6 GB+ allows the 8B model |
| **Radio** | None (use the built-in simulator) | Any Meshtastic device: Heltec, T-Beam, RAK, T-Echo... |

No GPU is fine. Answers just take longer (seconds to a minute on a CPU), which suits a mesh where messages
already take seconds to travel. The setup wizard detects your hardware and recommends a model that fits.

**No GPU, or not an NVIDIA one, with Docker:** nothing to do. The shipped compose file asks for no GPU, so Ollama runs both
models on the CPU. Only people who add the `deploy:` block from `docker-compose.override.example.yml` get the NVIDIA path, and
that needs the NVIDIA Container Toolkit. Indexing is the part that feels it: measured here, the embedding model ran about 20
chunks/s on CPU against 73 to 130 on an NVIDIA GPU, so a large Wikipedia file takes several times longer (it resumes if
interrupted, and the first pass makes every article findable early). AMD and Intel GPUs are not set up in the compose files and
have not been tested; they run on CPU unless you write your own override for them.

Software: **Docker** (easiest), or **Python 3.11+** and **Node.js 20+** for `./run.sh`. You also need
[Ollama](https://ollama.com) to run the language model (included in the Docker setup).

## Quick start

Internet is needed **once**, to fetch software, a model, and a Wikipedia file. After that it runs offline, apart from the
optional [update checks](#updates).

### Option A: Docker (recommended)

```bash
git clone https://github.com/TeamHarrisCali/LoRaPedia.git && cd LoRaPedia
docker compose up -d
```

Open **http://localhost:8000**. The first visit starts the setup wizard.

This pulls the signed release images and starts LoRaPedia, an Ollama server, and a small **updater** that keeps LoRaPedia
current (see [Updates](#updates)). Data lives in Docker volumes and survives restarts. **A USB radio needs nothing**: plug in any Meshtastic radio, before or after starting, and it is found (see below). For an NVIDIA GPU,
copy [docker-compose.override.example.yml](docker-compose.override.example.yml) to `docker-compose.override.yml` and edit it. Moving an
existing `./run.sh` install? See [docs/MIGRATING.md](docs/MIGRATING.md). Developing instead? `docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build`.

**Docker or not?** Docker is the supported, auto-updating path on Linux, Raspberry Pi 5 and Jetson. It has limits: Bluetooth
radios do not work inside a container; a USB radio is found automatically (the host's `/dev` is mounted read-only beside the
container's own and only USB serial ports may be opened; the container starts as root for a moment, with only the two capabilities needed
to take on the device's group, then runs the app as an unprivileged user: see the comments in [docker-compose.yml](docker-compose.yml)),
but a radio plugged in later whose group the container has not seen needs `docker compose restart lorapedia` once; the GPU needs the NVIDIA Container Toolkit; and Docker Desktop on Windows/macOS cannot pass USB devices through. For those,
use option B.

### Option B: without Docker

```bash
./run.sh
```

It creates a Python environment, builds the web UI, and starts the server on http://localhost:8000. Install and
start [Ollama](https://ollama.com) yourself first. To let other devices on your network open the UI:
`HOST=0.0.0.0 ./run.sh` (read [Security](#security) first). Bluetooth radios work with this option only. Updates are
announced but applied by hand (`git pull`).

### The setup wizard

Six steps, each skippable and revisitable. Progress is saved, so closing the tab is fine.

1. **Check this computer.** Shows what hardware was found.
2. **Pick a language model.** Recommends one for your hardware and installs it with a progress bar. Short on
   time? "Use demo mode" lets you try everything with nothing to download.
3. **Connect your radio.** Plug it in and press Retry, or use the simulator.
4. **Add Wikipedia.** Use the 12-article sample, a file you have, or download one (see below).
5. **Build the index.** Make it searchable. Start with a small subset and expand later.
6. **Test it.** Asks a question end to end.

No radio yet? Everything works with the **simulator**: type as a fake node from the Dashboard. Nothing is
sent over the air.

## Getting Wikipedia files

On the **Knowledge** page (and in the wizard) pick a Wikipedia **package** and press **Install**. LoRaPedia downloads
it from [Kiwix](https://www.kiwix.org), adds it to the library, and builds the search index, all in one step.
The newest version is looked up when you press the button. This is the only part of LoRaPedia that goes online,
and only when you press it. Downloads show progress and speed and **resume** if interrupted.

| Package | Download | Free space to plan for\* | What it is |
|---|---|---|---|
| **Quick Reference** (recommended) | ~300 MB | ~1.2 GB | The most-read articles, introductions only |
| Popular Articles | ~2.2 GB | ~9 GB | The same articles with their full text |
| Complete (Compact) | ~12.5 GB | ~50 GB | Every English article, introductions only |
| Complete (Full Text) | ~53 GB | ~210 GB | Every article, full text. Very large |

\* The search index is stored beside the download and is **about three times larger than it**, because each chunk of
text stores a 768-number vector. That ratio was measured on Quick Reference only; the larger rows apply the same
factor and full-text editions have more chunks per article, so treat them as optimistic. The installer refuses to
start if the disk is too small, and refuses *before* downloading if the embedding model is missing.

Image editions are not offered: LoRaPedia never uses images.

**Two-pass indexing (the default).** Indexing runs in two passes so every topic works early. **Pass 1** indexes the
opening of every article across the whole file; as soon as it finishes, any topic in the file can be found. **Pass 2**
then adds the rest of each article, improving detail. You can ask questions throughout. (The older "article by
article" order is still available; it finishes each article in alphabetical order, so only the early letters work
until it is done.) Both passes are safe to stop and resume.

**How long indexing takes.** It is dominated by the embedding model, which on one test laptop (RTX 3050 Ti,
`nomic-embed-text`) handled roughly 60 to 130 chunks per second. Quick Reference has about 50,000 real articles and
roughly 200,000 chunks, so pass 1 (one chunk per article) is on the order of ten minutes, and the whole job roughly
an hour or two, depending on what else is using the GPU.

**Counting articles.** Kiwix files list redirects as articles, and over 90% of a Wikipedia file's entries are
redirects. LoRaPedia estimates the real article count by sampling, so figures are shown as "about".

Other ways to add a file (Knowledge page, *Other files and advanced options*):

- **Import a file you already have.** Enter its path.
- **Copy it** into the `zim/` folder inside the data directory and restart.
- **Paste a Kiwix link**, or browse every English Wikipedia variant Kiwix lists.
- **The 12-article sample**, to try everything before downloading anything.

**Indexing a subset.** In "article by article" mode you can index "first 10,000" or "intro only". "First N" means the
first N in the file's own order, which is alphabetical, **not** the most popular, so a partial index is lopsided.
The two-pass default avoids this: prefer it.

If you change the embedding model after indexing, the index must be rebuilt (different models make incompatible
vectors). The installer asks before doing this, and your files are never deleted by it.

## Setting up the Meshtastic radio

Short version. Details and tips are in [docs/MESHTASTIC.md](docs/MESHTASTIC.md).

1. **Flash current firmware** with the [Meshtastic web flasher](https://flasher.meshtastic.org) (Chrome or Edge).
2. **Set your region** (required before it will transmit), a device name, and any channel settings.
3. **Plug it into the computer running LoRaPedia** with a USB cable that carries data (some are charge-only).
   On Linux, add your user to the serial group (`dialout` on Debian/Ubuntu, `uucp` on Arch) and log in again.
4. In LoRaPedia go to **Radio**, choose *Automatic (USB)*, and press **Connect**.

Prefer WiFi? Enable WiFi in the radio's network settings, then choose *Network* and enter its address. Bluetooth
is supported too, outside Docker.

Dedicate a radio to LoRaPedia. Give it a memorable name (e.g. `WIKI`) so people know who to message.

## Using it

Anyone on the mesh can **send a direct message** to the LoRaPedia node with their question, and only the asker sees the reply.
**LoRaPedia answers direct messages only. It never replies in a public channel, and anything said in a channel is ignored.** That is
not a setting: the rule is enforced at four separate points (the message parser, the engine, the radio manager, and the radio
adapter, which has no way to broadcast at all), each with its own test, so a wrong setting, an old settings file or a bug in one place
cannot make the node post publicly. A prefix such as `?what is a quasar` or `!wiki quasar` is optional in a direct message.

| Message | What happens |
|---|---|
| any question | Searched, answered, and sent back |
| `?help` | Short usage hint |
| `?more` | Next part of a long answer (when parts are sent on request) |
| `?stats` | Questions today, average time, queue length |
| `?ping` | A range test: how your message reached the node ("heard you directly: SNR 5.5 dB, RSSI -42 dBm", or how many relays it passed through and the signal of the last hop). Needs no model |

**When Wikipedia has nothing.** If a question matches no article, LoRaPedia does not just say "not found". Once every
article is searchable (after pass 1), it asks the language model to answer **from its own memory**, and the reply
always starts with **`[AI memory - may be wrong]`**. That warning is added by the program, not left to the model. A guess
is never sent as more than **one message**, however long the model rambles, because it is the least reliable thing
the node sends.
A small model gets facts wrong, so treat these as hints: the model is told to say "I don't know" rather than guess,
and to keep medical, legal and safety questions general. While indexing is still on pass 1, an unmatched question
gets "Not found yet: my library is still being indexed" instead, because the article may simply not be indexed yet.
Turn this off under *Settings → Answers* to get a plain "not found". Guesses are marked "AI memory, unverified" in the
Live Feed. One caveat: a detail buried deep in an article may not be indexed until pass 2 finishes, so the model may
answer that from memory even though Wikipedia has it; the warning covers that case too.

**Message size.** A Meshtastic text message holds about 233 bytes. LoRaPedia counts **UTF-8 bytes, not
characters** (accented letters and symbols cost 2 to 4), and uses a configurable limit, **200 by default**. An
answer is made to fit like this:

1. The model is asked for a short answer within the limit.
2. If it is too long, it is asked **once** to compress it.
3. If still too long, it is cut at a word boundary and ends with `...`. This last step guarantees the limit.

**Long answers.** If an answer genuinely needs more room, LoRaPedia can send it as numbered parts like `(1/3)`,
each within the limit, up to a **maximum number of parts you set** (default 3). Parts go out one after another
with a pause between them, or the first part goes out and the rest wait for `?more`. Turn this off to always
send one message.

**Fair use of the airwaves.** Each node is limited to **1 question per 60 seconds** by default. A question that comes
too soon is **not rejected**: it is held and answered when its turn comes, and the asker gets a short
"Queued. Answer in about 45s." so they know it arrived. Each node can have up to 3 waiting; beyond that, or when the
whole queue is full (20 by default), they get a "Busy" reply. Answers leave one at a time with a delay between
messages. All of this is adjustable, including switching back to plain "busy, try again in Ns" replies. You can
block nodes, or allow only listed ones, on the Radio page.

## Settings

Everything is editable in the UI; nothing requires environment variables. Where to find it:

| Page | You can change |
|---|---|
| **Radio** | Connection (USB / network / Bluetooth / simulator), trigger prefixes, hop limit, **byte limit (50 to 233)**, multi-part and its cap, pause between sends, node block/allow lists |
| **Model** | Language and embedding model (install with progress), temperature, max tokens, passages retrieved, system prompt (with *Reset to default*), a "try it" box showing the byte count |
| **Knowledge** | Wikipedia files, downloads, indexing, a search playground |
| **Map** *(beta)* | Every node with a known position on a plain offline grid with a scale bar: pan, zoom, search, filter by how recently it was heard, optional movement trails, and a card with distance from this radio. There is no background map picture, on purpose: LoRaPedia works without the internet |
| **Telemetry** *(beta)* | What nodes broadcast: sensor averages around you (each node counted once), battery, voltage, channel use, temperature, humidity and pressure over time for the nodes you pick, a table of recent readings, and a CSV export |
| **Trends** *(beta)* | When the mesh is busiest (by hour of the day), a heat map of the last week, and how far packets travel (directly, or through how many relays). Counts only |
| **Nodes** *(beta)* | Every node the radio has heard: names, hardware, hops, signal, battery, sensors, last position, and a history of each. Search and filter, and add your own label and note to any node |
| **Settings** | Rate limits, queue length, AI-memory fallback, theme, temperature and distance units, backups, mesh data, CSV export of the log, demo data |

Environment variables exist for deployment only: `LORAPEDIA_DATA` (data folder), `LORAPEDIA_HOST`,
`LORAPEDIA_PORT`, and `LORAPEDIA_OLLAMA_URL` (where Ollama is, used for first-run defaults).

**Backups.** *Settings → Backups* takes, downloads, uploads and restores backups of your **settings and question log** (a few
hundred KB). One is taken automatically every day (the newest seven are kept), before every update, and before every restore, so a
restore can always be undone. They are kept in `backups/` inside the data folder, so they protect against a bad change or update,
not against losing the disk or Docker volume: download one now and then. A backup does **not** include the Wikipedia files or their
search index (gigabytes; download and re-index them). To save those too, copy the whole data directory.

**Sources.** The replies over the radio carry no source tag, because every byte is airtime. The Live Feed shows which Wikipedia
articles each answer came from, the one that best supports the answer first.

## Updates

LoRaPedia and its Wikipedia can keep themselves current. These checks are the only things it does online without being asked,
and each has a switch under **Settings → Updates**. Nothing else is sent anywhere: no telemetry, no analytics, no identifier.

**LoRaPedia itself.** About once a day it asks `api.github.com` for this repository's latest *stable* release (one small request;
only your IP address and the version `lorapedia/0.1.0` are visible to GitHub). If a newer one exists:

| Install | What happens |
|---|---|
| **Docker with the updater** (the default compose file) | Applied **automatically** once the node has been quiet for a few minutes: nothing queued, nothing downloading or indexing, no question answered recently. A verified backup of your settings and log is made first. |
| Docker without the updater | You are told, with the two commands to run (`docker compose pull`, `docker compose up -d`). |
| `./run.sh` / source checkout | You are told, with the commands (`git pull`, `./run.sh`). |

**Beta channel.** *Settings → Updates → Release channel → Beta* also offers test versions (`vX.Y.Z-beta.N`) built from the `beta`
branch, checked and signed like any release. **Return to stable** in the same card brings a beta back to the newest stable release (the one downgrade there is). See [docs/UPDATING.md](docs/UPDATING.md#the-beta-channel).

**How the automatic update is made safe.** The app never touches Docker. A separate, minimal *updater* container holds the
Docker socket, and it can do exactly one thing: install the newest published release of *this* repository.
- It takes **no instructions** from the app: it looks up the release on GitHub itself, so a compromised app cannot make it
  install anything else, an older version, or from another registry.
- It pulls the image and verifies its **cosign signature** against the exact identity of this repository's release workflow
  for that exact tag (only the release workflow, run on that tag, can produce a passing image). An image that fails is deleted.
- What was verified is what runs: the image is pinned by **digest**.
- The new container must become healthy **and** report the new version within three minutes, or the previous version is put
  back automatically, and the failed version is not retried.
- Release builds are produced by GitHub Actions with every action pinned to a commit, publish only from a tag, and carry
  a build-provenance attestation. Details and how to check them yourself: [docs/UPDATING.md](docs/UPDATING.md).

The honest limits: you are trusting this GitHub account and its release workflow (restricting who can create release tags is
part of [docs/RELEASING.md](docs/RELEASING.md)); the updater holds the Docker socket, which is root-equivalent on the host,
which is why it is a separate tiny container rather than part of the app; and the automatic path is covered by unit tests
with a fake Docker and a fake GitHub **and** has been exercised for real: an update between two published, signed releases
(0.1.1 to 0.1.2) completed against a real Docker daemon, and the first attempt (0.1.0 to 0.1.1) failed safely at a real bug that
was then fixed. What has not run yet is the fully *unattended* trigger (the quiet-node timer), only the same code path started
by the button, and there is no long record of real updates. Turn **Install them automatically**
off if you would rather click *Update now*.

**Wikipedia.** About once a day it asks `download.kiwix.org` which edition of each installed package is newest (Kiwix publishes
roughly monthly). If one is newer, and the setting allows, it downloads and indexes the new edition **beside** the old one and
removes the old one only when the new one is fully ready. It only touches packages you installed (and only their older
edition, never your own files), only when the node is quiet, never without enough disk space for the new edition and its
index, and never rebuilds your index on its own. If it cannot start, Settings says why and it tries again a day later.
Updating takes a while (a download, then re-indexing) and questions keep being answered meanwhile.

**Mesh data** *(beta)*. To build the Nodes page, LoRaPedia remembers what the radio hears from other nodes: their names, hardware,
last known position, battery and sensor readings, signal strength and how many relays a packet passed through. It never keeps the
content of any message. It stays on this computer in `mesh.db` (separate from your settings and question log, and not part of
*Backups*), history is deleted after 30 days by default (a node not heard for 90 days is forgotten, and position trails live three
times as long), and *Settings → Mesh data* turns the recording off or changes the retention. Positions are location data: keep that in
mind before sharing the file or the screen. Your labels and notes are never deleted by the clean-up and never sent over the radio.

## Security

**The web interface has no password.** Anyone who can open it can change settings, delete the library, and start
downloads. So:

- By default it listens on **this computer only** (`127.0.0.1`). The Docker setup is published the same way.
- Only open it to your local network (`HOST=0.0.0.0` or changing the port mapping) on a network you trust.
- **Never expose it to the internet.** If you need remote access, put it behind a VPN or an authenticating proxy.

The **updater** container holds the Docker socket (root-equivalent on the host). It is separate from the app on purpose, listens only
on the private compose network, accepts no parameters, and only installs signed releases of this repository; remove the `updater`
service from `docker-compose.yml` if you would rather update by hand.

Text arriving from the mesh is untrusted input. LoRaPedia only ever turns it into a search and a text reply. The
model has no tools and cannot run anything, so the worst outcome of a hostile question is a bad answer.

## Troubleshooting

| Symptom | What to do |
|---|---|
| **"No radio found. Is it plugged in?"** | Check the USB cable carries data (try another). Press Retry. Run `ls /dev/ttyACM* /dev/ttyUSB*`: if nothing appears, the computer does not see the radio. Meanwhile the simulator keeps everything usable. |
| **The radio will not connect (Linux)** | The Radio page now looks at the real device files and tells you which of the usual causes it is, with the exact commands to copy: a cable that only charges, your user (or the container) not being in the device's group, a device file that its group may not write to (it offers a udev rule), another program holding the port (ModemManager, the Meshtastic app), or a radio that does not answer. |
| **"Permission denied" on the serial port** | Add your user to the serial group (`sudo usermod -aG dialout $USER`, or `uucp` on Arch) and log out and in. In Docker the container learns the device's group when it starts: run `docker compose restart lorapedia`. |
| **"The serial port is busy"** | Another program has it: the Meshtastic app or CLI, or ModemManager on Linux. Close them, or stop ModemManager (`sudo systemctl stop ModemManager`). |
| **"Several radios found"** | Choose *USB, choose the port* and pick one. |
| **Radio connects but nobody gets answers** | The node answers **direct messages only**: send the question to this node directly, not in a channel. Look at the Live Feed to see whether the question arrived. |
| **"LLM not ready" / "Cannot reach Ollama"** | Start Ollama (`ollama serve`, or the `ollama` container). In Docker the address is `http://ollama:11434`. See the Model page. |
| **"Model … is not installed"** | Install it from the Model page, or `ollama pull <name>`. |
| **Indexing fails: embedding model not installed** | Install `nomic-embed-text` on the Model page, or turn on *Keyword-only search* there to index without one. |
| **"Re-index needed"** | The index was built with a different embedding model. Remove the library entry and index again. Keyword search keeps working meanwhile. |
| **"Not found yet: my library is still being indexed"** | Indexing is on pass 1, so the article may not be searchable yet. Check the Knowledge page. |
| **Every answer is "Not found in my offline library"** | Nothing relevant was retrieved. Open the question in the Live Feed to see what was found, and use the search playground. Is the right file indexed? Is only the demo data loaded? |
| **Indexing is much slower than expected** | Check where the embedding model is running: `ollama ps` should show it on `100% GPU`. If it shows mostly CPU (this happened on a 4 GB card when the chat model had loaded first and taken the memory), run `ollama stop llama3.2:3b` and `ollama stop nomic-embed-text`; the embedder reloads onto the GPU on its next request. Measured here: 20 chunks/s on CPU, 73 on GPU. |
| **First answer is very slow** | The model is loading into memory. Later answers are faster. |
| **Answers end in `...`** | They were cut to fit. Allow more parts, raise the byte limit (up to 233), or lower *max tokens*. |
| **"Busy: N of your questions are already waiting" / "Busy, try again later"** | The sender already has the most questions allowed waiting, or the whole queue is full. Both limits are under Settings. Questions inside the cooldown are normally queued, not rejected. |
| **Page is blank or looks broken after an update** | Hard-refresh the browser (Ctrl+Shift+R). |
| **Download fails or stalls** | It keeps its progress: press Resume. This step needs internet; everything else does not. |
| **"The updater could not be reached"** | The `updater` container is not running (`docker compose ps`), or you removed it. Without it, updates are by hand: `docker compose pull && docker compose up -d`. |
| **An update "rolled back"** | The new version did not become healthy, so the previous one was restored. Settings → Updates says why; that version is not retried. Check `docker compose logs lorapedia`. |
| **Bluetooth radio not found in Docker** | Not supported in Docker. Use `./run.sh`. |

Still stuck? The server prints a log (`docker compose logs lorapedia`, or the terminal running `./run.sh`).

## Development

```bash
# backend (Python 3.11+)
cd backend
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/pytest                         # 150+ tests; no hardware or models needed
.venv/bin/python -m lorapedia            # API on :8000

# frontend (Node 20+), in another terminal
cd frontend
npm install
npm run dev                              # http://localhost:5173, proxies /api and /ws to :8000
npm run build                            # outputs frontend/dist, which the backend serves
```

Layout:

```
backend/    FastAPI app (lorapedia/), tests (tests/)
frontend/   React + Vite + TypeScript + Tailwind UI
docker/     Dockerfiles: the app (multi-stage) and the updater
updater/    the updater container's program
scripts/    release checks used by CI
docs/       Meshtastic setup, updating, and releasing guides
```

The tests cover the byte-limit and splitting logic (including multi-byte text), trigger parsing, rate limiting,
the message engine, the ZIM reader and indexer, retrieval, the radio adapter (against a fake device), the
downloader, and the API. The web UI was tested by hand in a browser; it has no automated tests yet.

Architecture and the message flow are in [ARCHITECTURE.md](ARCHITECTURE.md). Cutting a release: [docs/RELEASING.md](docs/RELEASING.md).

## Design decisions

Where the build departs from the original brief or chose a default for something unspecified:

- **Plain `sqlite3`, not SQLModel/SQLAlchemy.** The schema is small and fixed, so an ORM adds dependencies
  without helping.
- **Multi-part answers are on by default**, capped at 3 parts, as requested ("send in chunks if need be, up to an
  admin-specified amount"). The brief had it off by default. Turn it off on the Radio page.
- **The retrieval rerank is lexical**, not a neural cross-encoder: hybrid BM25 + vector search is fused, then
  re-scored by title match and query coverage. It runs on any CPU. A cross-encoder could slot in later.
- **A keyword-only fallback exists** (hashed vectors) so indexing works before any embedding model is installed.
  It matches words, not meaning.
- **"First N articles" is file order**, not popularity. A ZIM has no popularity data; use a `top_*` file.
- **The data directory is not changeable from the UI.** It cannot be moved while running; set `LORAPEDIA_DATA`
  or the Docker volume instead. The Settings page shows where it is.
- **The UI uses hash routes** (`/#/radio`), so the server needs no special URL handling.
- **The UI simulator uses a fresh fake node per test question**, so the per-node rate limit does not get in the
  way of quick tests.

## Limitations

- Verified on one real radio and real Wikipedia (the Quick Reference package, indexed with `nomic-embed-text`): a
  **RAK4631 over USB** exchanged a direct message with a phone-connected node and the answer came back (about 1.5 s
  with a local 3B model). Network and Bluetooth connections, other devices, and channel-mode replies are only tested
  against a fake radio.
- Only the Quick Reference package has been installed. The larger packages' download, indexing time and disk use are
  extrapolated, not measured.
- Retrieval quality was spot-checked on a few dozen questions, not benchmarked.
- English Wikipedia only has been considered; other languages should work if the ZIM is HTML but are untried.
- One radio at a time.
- Automatic updates: verified for real from 0.1.1 to 0.1.2 (signed releases, a real Docker daemon, including the roll-back
  mechanics), triggered by the *Update now* button. The unattended trigger (waiting for a quiet node, then applying) is covered by
  unit tests only, and the updater image and your `docker-compose.yml` are not updated automatically (see docs/UPDATING.md).
